# 架构优化设计方案：数据驱动 + dataService 收口

> 关联 Issue：#5 项目结构优化调整
> 参考项目：[deliton/eldenring-api](https://github.com/deliton/eldenring-api)（★271, JavaScript）
> 状态：设计草案，待评审后分阶段落地

---

## 1. 背景与目标

### 1.1 现状

DarkSouls-Tomb 是一个 Vue 3 + Vite + TypeScript 的多语言黑魂系列文本数据库（1/2/3 代、5 类物品、约 3000+ 条数据、100+ NPC 对话）。数据以静态 JSON 形式存放在 `src/data/ds{1,2,3}/` 下。

### 1.2 当前痛点

| # | 痛点 | 具体表现 |
|---|------|---------|
| 1 | **数据加载逻辑分散** | `useGameData.ts`、`DialogueView.vue`、`FavoriteView.vue` 三处各自 `import()` JSON，路径拼接、错误处理、加载态各写一套 |
| 2 | **类型安全缺失** | `useGameData` 返回 `Item[]` 但动态 import 的 JSON 是 `any`，运行时字段错误无法在编译期暴露 |
| 3 | **元数据未利用** | 每条数据已带 `game` / `type` 字段，但 `FavoriteView` 通过 `id.split('-')[0]` 字符串解析推断游戏/类型，脆弱且绕远 |
| 4 | **常量过期** | `utils/constants.ts` 中 `ITEM_COUNTS`（如 ds2 armor 写 481）与实际数据文件（484）不一致，人工维护必然漂移 |
| 5 | **NPC 列表硬编码** | `DialogueList.vue` 中手写了 140+ 个 NPC 名字符串数组，与 `src/data/ds*/dialogues/*.json` 实际文件存在大量不一致（DS2 列表 58 个含 31 个无文件、漏 21 个有文件） |
| 6 | **查询逻辑重复** | 搜索过滤（名称/描述、多语言）在 `ItemCatalogTable.vue`、`FavoriteView.vue` 等处重复实现 |
| 7 | **全量加载无缓存** | `FavoriteView` 一次性 `Promise.all` 拉 15 个 JSON（约 7MB+），每次进入页面重复加载 |

### 1.3 目标

- **数据驱动**：以 `src/data/` 下 JSON 为唯一事实源，界面数据完全由数据层驱动，消灭硬编码清单与过期常量。
- **dataService 收口**：所有数据访问收敛到统一 `services/dataService`，视图/组合式函数不再直接 `import()` JSON。
- **类型安全**：为数据文件提供类型化入口，编译期即可发现字段错误。
- **性能**：模块级缓存 + 按需加载 + 并发请求合并，减少重复全量加载。

## 2. 参考项目调研：eldenring-api 的核心模式

`deliton/eldenring-api` 是一个 ★271 的成熟开源项目（FromSoft 游戏资料 RESTful/GraphQL API），其架构可概括为 **“静态数据 + 统一访问层 + 薄路由”** 三段式：

### 2.1 数据存放

```
api/public/data/weapons.json
api/public/data/armors.json
...
```
纯静态 JSON，游戏内容变更时只需改 JSON、提 PR，无需改代码 —— 这是“数据驱动”的根基。

### 2.2 数据访问层（本项目核心参考点）

`api/db/loader.js` —— **模块级缓存加载器**：

```js
var data = {};
export const JSONLoader = async (model) => {
  if (!data[model]) {
    data[model] = JSON.parse(await readFile(`./public/data/${model}.json`));
  }
  return data[model];
};
```

`api/db/driver.js` —— **链式查询 Driver**（`findMany` / `findById` / `search` / `skip` / `limit` / `join`），一次 init 后所有查询走统一管道，且支持多模型 join（如物品关联 NPC）。

### 2.3 路由层（薄封装）

每个资源仅一个端点文件 + 复用 Handler：

```js
// api/pages/api/weapons/index.js
import { simpleJSONGetAllHandler } from "utils/requestHandlers";
export default async function handler(req, res) {
  return simpleJSONGetAllHandler(req, res, "weapons");
}
```

### 2.4 对本项目的映射

| eldenring-api | DarkSouls-Tomb 对应物 | 借鉴点 |
|---|---|---|
| `public/data/*.json` | `src/data/ds*/**.json` | 静态 JSON 即唯一事实源（已具备） |
| `db/loader.js` 模块级缓存 | **`services/dataLoader.ts`（待新建）** | 模块级缓存，同一模型只加载一次 |
| `db/driver.js` 链式查询 | **`services/dataService.ts`（待新建）** | findById / findMany / search 统一管道 |
| 薄路由 + Handler | 视图直接消费 service | 视图不再感知 JSON 路径 |

## 3. 目标架构

### 3.1 新增目录结构

```
src/
├── services/                  # 数据服务层（新增，唯一数据入口）
│   ├── dataLoader.ts          # 模块级缓存 + 动态 import JSON
│   ├── dataService.ts         # 面向业务的高层 API（物品/对话）
│   ├── itemService.ts         # 物品领域查询（可选拆分）
│   └── dialogueService.ts     # 对话领域查询（可选拆分）
├── types/
│   └── item.ts                # 现有类型（保持）
├── composables/               # 保留，但只做“状态编排”，不再碰 import()
│   ├── useGameData.ts         # 改为调用 dataService
│   └── ...
```

### 3.2 核心：dataLoader.ts（参考 JSONLoader）

```ts
// src/services/dataLoader.ts
import type { Item, Dialogue } from '@/types/item'

type DataModel = 'items' | 'dialogues'

const cache = new Map<string, unknown>()

/** 加载物品数据：ds{game}/{type}s.json */
export async function loadItems(game: GameVersion, type: ItemType): Promise<Item[]> {
  const key = `item:${game}:${type}`
  if (!cache.has(key)) {
    const module = await import(`@/data/ds${game}/${type}s.json`)
    cache.set(key, module.default as Item[])
  }
  return cache.get(key) as Item[]
}

/** 加载对话数据：ds{game}/dialogues/{npc}.json */
export async function loadDialogue(game: GameVersion, npc: string): Promise<Dialogue> {
  const key = `dialogue:${game}:${npc}`
  if (!cache.has(key)) {
    const module = await import(`@/data/ds${game}/dialogues/${npc}.json`)
    cache.set(key, module.default as Dialogue)
  }
  return cache.get(key) as Dialogue
}

/** 预加载某游戏全部类型（收藏页场景） */
export async function loadAllItems(): Promise<Item[]> {
  const games: GameVersion[] = [1, 2, 3]
  const types: ItemType[] = ['weapon', 'armor', 'ring', 'item', 'magic']
  const results = await Promise.all(
    games.flatMap((g) => types.map((t) => loadItems(g, t).catch(() => [])))
  )
  return results.flat()
}
```

要点：
- **模块级 `Map` 缓存**：同模型进程内只加载一次，收藏页/详情页共享，避免重复拉取 7MB+。
- **类型化返回值**：`as Item[]` 将 JSON 收口为强类型，后续可加运行时校验（见 §5.5）。
- **并发合并**：`loadAllItems` 用 `Promise.all`，且天然去重（缓存命中）。

### 3.3 数据驱动：NPC 清单不再硬编码

`DialogueList.vue` 目前手写 140+ NPC 名数组。数据驱动方案二选一：

**方案 A（推荐）**：新增 `src/data/ds{game}/dialogues/index.json` 索引文件（或 `manifest`），内容为 NPC 清单（含头像路径等展示元数据），由构建脚本/手写维护：

```json
// src/data/ds1/dialogues/index.json
["alvina", "anastacia", "andre", "..."]
```

`dialogueService.listNPCs(game)` 读取该索引，替代硬编码数组，并可直接对缺失头像做兜底。

**方案 B**：构建时用 Vite `import.meta.glob` 生成清单：

```ts
// services/dialogueService.ts
const dialogueGlob = import.meta.glob('@/data/ds*/dialogues/*.json')
// 从 key 中解析 game / npc，自动获得全量清单
```

方案 B 零维护、天然跟随文件系统，是更彻底的“数据驱动”，推荐作为后续优化项（详见 §5.6）。

### 3.4 高层 API：dataService

```ts
// src/services/dataService.ts
export const dataService = {
  // 物品
  getItems: (game, type) => loadItems(game, type),
  getItemById: async (game, type, id) =>
    (await loadItems(game, type)).find((i) => i.id === id),
  getAllItems: () => loadAllItems(),
  getFavoriteItems: (ids: string[]) =>
    loadAllItems().then((all) => all.filter((i) => ids.includes(i.id))),

  // 对话
  getNPCList: (game) => listNPCs(game),
  getDialogue: (game, npc) => loadDialogue(game, npc),

  // 元数据（数据驱动，替代过期常量）
  getItemCounts: async () => {
    const items = await loadAllItems()
    const counts: Record<GameVersion, Record<ItemType, number>> = {
      1: { weapon: 0, armor: 0, ring: 0, item: 0, magic: 0 },
      2: { weapon: 0, armor: 0, ring: 0, item: 0, magic: 0 },
      3: { weapon: 0, armor: 0, ring: 0, item: 0, magic: 0 }
    }
    for (const it of items) counts[it.game][it.type]++
    return counts
  }
}
```

### 3.5 视图改造示例

`FavoriteView.vue` 从“字符串解析 id + 全量重复加载”改为：

```ts
// before
const game = id.split('-')[0]          // 反模式：解析字符串
// after
const game = item.game                 // 数据自带元数据
const type = item.type
```

`ItemCatalog.vue` / `ItemDetail.vue` 的 `useGameData` 内部改为调用 `dataService.getItems(game, type)`，对外 API 不变，改动面最小。

## 5. 收益与风险

### 5.1 收益
- **单一数据入口**：改数据结构只动 service，视图零感知。
- **编译期安全**：类型化 JSON，字段写错直接报错。
- **性能**：模块级缓存使收藏页从每次 15 个请求降到首屏 1 次、之后 0 次。
- **可维护性**：删除硬编码 NPC 清单、过期 ITEM_COUNTS、字符串解析 id 等隐患。
- **可测试性**：数据层纯函数化，可单测。

### 5.2 风险与对策
| 风险 | 对策 |
|---|---|
| 动态 import 路径变更导致构建产物分块变化 | 保持 `src/data/ds{game}/...` 路径约定，Vite 分块策略（按游戏拆分）不受影响 |
| 缓存导致开发期数据修改不生效 | dev 模式 `import.meta.hot` 时清空对应 cache key，或提供 `clearDataCache()` |
| JSON 体积大（收藏页全量 ~7MB） | 阶段 1 沿用现有全量加载行为；后续可基于 index 做 id 级按需加载 |
| `import.meta.glob` 与 PWA precache 的兼容 | 阶段 2 验证；若冲突退回方案 A（索引文件） |

### 5.3 后续建议（超出本次范围）
- 对话数据缺失字段兜底与头像 404 处理统一收口。
- 图片资源（public/icons）继续按数据 index 驱动，删除孤儿图标。
- 引入 Vitest 对数据层/搜索逻辑做单元测试，接 CI。
